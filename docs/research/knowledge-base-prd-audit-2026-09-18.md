# Solar24 知识库复审与 PRD 回归 · 2026-09-18

**结论：研究资料库已经可用，上一轮修复有实际成效，但还没有形成一份可发布的文化内容样本。下一阶段应围绕立春完成“证据核验 → 双语解释 → 人工审核 → 显式生产内容 → 理解测试”的最小闭环，停止以卡片数量作为主要进度指标。**

本轮只审计并提出建议。未改知识卡、审核状态、协议或业务代码；未提交、推送或发布。历史审计及修复报告保留。

## 4. 仍需解决的发现

### R01 · P1 · 清明英文保留已否定的旧断言

[清明解释](../../knowledge-base/03_notes/qingming-human-explanation.md)第 28–29 行：中文已改成法定节假日语境，英文仍写 `the only one ... that also grew into a major traditional festival`。修改记录明确说这个历史排他判断已被冬至反例否定，英文却未同步。

[路由器](../../skills/solar24-cultural-research/workflows/route.ts)第 378–407 行只比较整层是否出现强量词。中文有“唯一”，英文有 only，便不会报告两者限定的是不同命题。当前实际路由只返回 explanation-gated，没有检出此处错误。

建议：修复具体英文并审查新中文判断的司法辖区、时间范围及依据；增加这一真实漏检的回归样例。关键词规则只能辅助，逐句双语对照仍是必要验收，不能把“零新增 finding”写成“语义全部正确”。

### R02 · P1 · 立春参考内容还不是可审核完成的最小样本

[立春解释](../../knowledge-base/03_notes/lichun-human-explanation.md)第 31–42 行仍有“此时中国大部仍然寒冷”“更多地方吃春饼”等已被原审核标为 Unsupported 或需改写的句子。当前路由仍报告两个 unsupported-distribution 和一个 modern-spread-over-historical-scope，另有正常的未批准门禁。

另有实际证据范围丢失：解释把九华与石阡合并为“按立春日祭祀劝农”，展开版称石阡说春“仍按立春日举行”。[石阡知识卡](../../knowledge-base/03_notes/region-shiqian-shuochun.md)及本次直读原页写的是“春节或立春时开始，春分时结束”，形式是春官说唱。不能把不同地方的活动统一成一个节气日的祭祀。

Frontmatter summary 写“春饼或春饼类食物”，正文仍写“春饼或春卷”，文本投影也未完全同步。英文 `yachun` 与中文“咬春”读音不符，应在术语审核中处理。

建议：先删减或收窄不受支持的句子；地区案例选一到两个，保留各自时间与形式。先做一份忠实而短的立春解释，再推广到其他节气。不得把“已有审核问题清单”当作问题已经解决。

### R03 · P1 · 同源注记未进入路由，局部审核也缺少可执行边界

[小满三候](../../knowledge-base/03_notes/hist-yueling-xiaoman-pentads.md)正文现已明确“独立证据方仍为 1”，当前引擎却返回 `independence: 2 / auto-candidate`；谷雨同构卡也如此。[路由器](../../skills/solar24-cultural-research/workflows/route.ts)第 144–148 行仍仅按 publisher 字符串去重。

这不意味着同一原典不能支持“该书如何记载”，而是字段所称的独立性与实际证据含义不同。必须区分单原典文本核对和独立证据互证。

[小满农事卡](../../knowledge-base/03_notes/trad-xiaoman-nongshi.md)第 53–62、86 行增加了子命题映射并建议“分项 Decision”，但 Frontmatter claim 仍混合多项叙述、待核食物史和转述。现有 KnowledgeSchema 只提供整卡一个 human_review，没有分项批准机制。

建议：优先对准备发布的复合卡拆出最小可审核命题，或缩小 claim，把未核子命题留在研究正文；不必全库重构。路由中的发布方多样性应如实命名，同源关系或人工判定应有机器可读的记录；在此之前对已知同源卡保守送审。不得把一项获批解释为整卡获批。

### R04 · P1 · 审核总包仍给出互相冲突的操作指令

[统一审核包](../../knowledge-base/07_research/solar24-batch-human-review-package.md)第 33 行仍写“A 区无需逐卡审核，抽检即可”，第 42 行仍写“不必逐卡审”及 B 类“不阻塞”；同文件新说明和研究规范却要求发布前逐卡留真实记录。

此外，审核表使用 approve/revise/hold/reject，Schema 的 human_review.decision 使用 approved/changes-requested，笔记另有 draft/in-review/approved/withdrawn 状态。可保留人类便于使用的词，但必须明确从表格决定到正式数据的映射、操作人和对应版本，避免“表中点了批准”与实际数据脱节。

建议：清理当前操作说明中的旧句；明确抽检只用于库存质量评估，**只有选入首版内容的卡必须逐卡完成发布审核**。不要求负责人先审完全库，也不允许未审库存随抽检获批。

### R05 · P1（首次内容导入前）· 共享知识无法通过当前生产关联检查

[Vault 规范](../../knowledge-base/00_project/guide.md)要求共享卡 `solar_terms: []`，禁止向各节气复制。[生产验证](../../scripts/validate.ts)第 75–80 行却要求 approved 内容引用的每张知识卡都满足 `note.solar_terms.includes(slug)`。

例如共享的 `sci-solarterms-calendar-role` 的 solar_terms 为空，因此未来即使经过真实批准，立春引用它仍会被判 `Knowledge term mismatch`。当前 24 个生产 claims 全空，所以全绿没有执行到这个实际用例。

建议：定义显式的共享知识适用规则，允许合法 system/shared 卡、继续拒绝其他节气的私有卡；用纯测试夹具验证两种路径，不修改真实审核字段。这个小范围契约修复应在首次内容导入前完成，不能通过复制共享卡绕过。

另外，HumanExplanation 当前被 assertPublishableNote 排除，生产 content 又没有解释审核引用；未来需要明确“已批准解释如何变成生产文案、怎样证明翻译审过”的人工 PR 或最小数据关联步骤。尚无导出器是已知阶段边界，不要求现在开发全自动同步。

### R06 · P2 · 知识覆盖与“普通人理解”的覆盖并不相同

24 张解释的一句话全部含“黄经”，标称“约100字”的 summary 实际为 **141–258 个字符（含标点）**，英文 expanded 全部为空占位。天文精确性重要，但术语前置、长句和历史材料密集，尚不能证明零背景读者能理解。

生态标签主要对应古籍，不构成现代物候验证；地方差异卡存在，但现代当地人的经验和当代生活观察不足。24 张全球条目都是研究候选，没有真实投稿，这与当前阶段相容，不能当作 PRD 全球参与目标已经实现。

建议：评价单位改为“读者能回答的问题”，自然维度同时标明传统记载、现代机制、地方观测分别有无证据。先补立春故事所必需的缺口，不批量填满所有维度。

## 5. 回归 PRD 的验收矩阵

| PRD 核心要求 | 当前判断 | 下一步的最小验收 |
|---|---|---|
| 向世界讲明白节气是什么、为何存在 | 研究材料具备；解释草稿未核准 | 立春 3–5 分钟中英故事，术语可解释，无 Unsupported 句 |
| 太阳 → 自然 → 农业 → 生活 → 文化 | 文献与民俗较强；现代自然、实践层不均衡 | 一套准确机制、一个有范围的自然例子、一个有地点与时间的生活案例 |
| 事实有来源，AI 不代审 | 结构与门禁较好；来源语义和审核操作未收口 | 选入首版的每条断言有可定位证据及真实人工记录 |
| README 是第一件文化作品 | 根入口已具备方向；模块仍模板 | 立春 README 与已审核文案和实际预览一致，无虚构 Demo |
| 图像、声音、交互帮助理解 | 有创意提案，尚无已验收体验 | 先用一个轻交互解释一个问题，提供静态等价阅读；音频按需后置 |
| 双向邀请、尊重相似与差异 | 协议和候选已建立；尚无社区作品 | 保留开放问题与未来贡献路径，不把 AI 候选当作他人自述 |
| 模块复用、单仓库、可维护 | 工程基础成立 | 完成立春真实内容导入，解决共享卡适用冲突，再验证第二模块复用 |
| 研究库与生产数据分离 | 已做到；生产数据目前为空 | 一次显式、可审阅、可撤回的内容 PR，不做自动全库发布 |

当前最值得更新的活动 PRD 条目：明确立春首版读者、理解目标、选用事实清单、非目标、发布审核责任与验收方法。原始 V0.2 保留，不覆盖历史。每节气至少 4 张 high 是批研究流程门槛，不能替代产品验收，也不应为了凑小满数量阻塞立春。

## 6. 建议按三个工作包推进

### 工作包 A：收口质量与发布契约

范围：清明英文、立春解释、统一审核包、准备进入立春的证据卡、共享内容关联规则及对应测试。

- 修复 R01/R02/R04 的明确错误；复核 R03 中首版实际依赖的来源链。
- 形成一个小型“立春内容选择清单”：每条拟用句子、知识 ID、摘录定位、地域/年代、使用目的、未决问题。
- 明确整卡与子命题审核边界、表格 Decision 的数据落点。
- 修复 R05 并同步文档、消费者、必要的 Schema 导出；测试合法共享引用通过、跨节气误引失败、草稿和撤回记录不得发布。

退出条件：首版拟用句子没有未处置的已知错误；审核指令一致；共享内容通路可验证。AI 可完成准备、纠错与测试，不能代填最终人审。

### 工作包 B：完成立春的最小文化内容样本

不等待 586 条全部审核。初选约 6–8 个小命题，数量可按故事需要调整，覆盖：

1. 节气作为太阳周年位置标记，以及立春在这个序列中的位置。
2. 立春日期与春节不是同一套规则；具体日期需说明时区和适用范围。
3. 节气节点不意味着所有地方同时暖和；避免无范围的天气判断。
4. 一个明示为传统文本的自然观察，或一个有可靠资料的现代当地现象。
5. 一个地域生活案例：九华立春祭或石阡说春，活动形式与时间准确；无需两者全上。
6. 一个基于上述事实的文化解释，明确为解释而不是“所有中国人的统一自然观”。

复杂置闰算法、所有三候的现代考证、完整饮食地图、UNESCO 身份、17 张全球候选的补证均不必成为这条最小故事的前置条件。若叙事不使用就暂缓；使用了就纳入相应审核依赖。

产物：简短中英一句话、可折叠的短摘要、3–5 分钟完整故事、逐句证据表、必要术语说明。由负责人或具备相应知识的人核验事实；英文需真实读者/译者复核。AI 标注疑点和建议，不冒充这些角色。

退出条件：选用知识及来源真实获审、中文解释和英语表达获审、权利边界明确、没有未标注的推断；其余库存继续 draft/in-review。

### 工作包 C：一个轻体验，验证“讲懂了没有”

在 B 的内容获准后，显式写入立春 content/references，通过 PR 或本地可审阅 diff 留痕。无具体事实的布局和键盘交互原型可以在审核期间独立准备；待审文案不公开。

推荐首个互动：24 个节点的太阳位置示意，选中立春后回答“这个刻度说明什么、不说明什么”。标注为示意图，不冒充精确天体模拟或当地天气预报。提供键盘操作、减弱动效、无声音和静态说明。先不做春牛仪式游戏化、三候自动解冻或音乐，避免增加未经研究的含义。

建议邀请 5 位不了解节气的读者做形成性测试（不是统计学验证），给 3–5 分钟后用自己的话回答：

- 二十四节气用什么划分时间？
- 立春是否意味着所有地方同一天变暖？
- 能说出一个具体地方的人如何回应这个时间吗？
- 同一个时间在自己生活的地方有什么不同？

建议退出指标：至少 4 人能正确回答前三题，且能区分中国案例与全球邀请；第四题用于检验是否产生参与意愿，不按标准答案打分。误解回流修改解释，再考虑第二个节气；小样本成功不代表已证明全球普适性。

第二模块可以选择春分验证不同叙事需求，或选择雨水验证连续季节故事；依据立春反馈决定，不立即铺开余下 23 个体验。
